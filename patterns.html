PRODUCT DECISIONS

Where semantic decisions fit into ordinary products

These examples place semantic judgments inside existing systems. Retrieval, factual records and action policy remain separate components; the model interprets the context at particular points in the workflow.

Start with a working example: step through the agent walkthrough, then model its cost and latency.

The gap in normal software

Structured facts are easy to program

Conceptual pseudocode · not an SDK example

if transaction.amount > 10_000:
    require_approval()

The rule is explicit and deterministic.

Semantic facts are not

Conceptual pseudocode · not an SDK example

if message_actually_requires_my_attention(message):
    notify()

Humans understand “actually requires my attention.” Traditional code needs a growing pile of approximations.

LLMs made semantic interpretation programmable

But for a bounded decision, generating a response and parsing the answer is an indirect interface.

Jev exposes the judgment directly

Conceptual pseudocode · not an SDK example

p = Noul("Does this require the user's attention now?")
if p > threshold:
    notify()

Three shapes of product decision

NOUL

Gate

Should this happen? Needs reply? Is it relevant? Is this suspicious?

CHOICE

Route

Which team? Which tool? Which category? Which action?

SCORE

Rank

How relevant? How urgent? How good a match?

SEARCH

Retrieval handles scale. Jev handles relevance.

Search engines are already excellent at turning millions of documents into tens of plausible candidates. The difficult last mile is deciding which candidate actually satisfies the user's meaning.

Conceptual pseudocode · not an SDK example

hits = search.retrieve(query, top=50)

for hit in hits:
    hit.relevance = Score(
        state={query, hit},
        levels=["wrong", "weak", "useful", "strong", "direct answer"]
    )

return sort_desc(hits)

Cardinality: five semantic levels, repeated over 50 candidates. A ten-million-document corpus does not imply a ten-million-way Choice.

TOOL SEARCH

Find broadly, judge fitness, then choose

Embedding similarity can find tools that sound related to the request. Jev can answer the stronger question: “Can this tool accomplish the goal?”

Conceptual pseudocode · not an SDK example

tools = retrieve_tools(goal, top=40)
for tool in tools:
    tool.fit = Score("Can this tool accomplish the goal?")

shortlist = top(tools, 8)
chosen = Choice(shortlist)
authorize_then_execute(chosen)

Composition: retrieval → Score → shortlist → Choice → deterministic authorization.

NOTIFICATIONS

Interpret importance; keep delivery policy in code

Conceptual pseudocode · not an SDK example

importance = Noul(
    state={event, user_context, recent_notifications},
    question="Is this worth interrupting the user for now?"
)

threshold = .98 if quiet_hours else .85
if importance > threshold:
    notify()

Jev answers the semantic question. Quiet hours, rate limits and user preferences remain ordinary product policy.

SUPPORT & OPERATIONS

Replace keyword heuristics with explicit semantic signals

Conceptual pseudocode · not an SDK example

decision = jev.ask(ticket, {
    owner: Choice(["billing", "identity", "network", "product"]),
    urgency: Score(["routine", "important", "urgent", "critical"]),
    outage: Noul("Does this describe an active outage?")
})

priority = combine(decision.urgency, account.sla, incident.status)
route(decision.owner, priority)

The semantic interpretation becomes easier to state and test; SLAs and incident state remain hard facts.

RECOMMENDATIONS & COMMERCE

Add natural-language intent after candidate generation

Keep collaborative filtering, inventory and personalization. Jev can rerank the resulting candidates against a request such as “comfortable for standing all day, but doesn't look like a running shoe.”

Conceptual pseudocode · not an SDK example

candidates = recommender(user)
available = filter_inventory(candidates)
for product in available:
    product.fit = Score(state={request, product}, question="How well does this fit?")
return top(product.fit)

INBOX & CRM

Give ordinary objects semantic properties

Conceptual pseudocode · not an SDK example

signals = jev.ask(message, {
    needs_reply: Noul("Does the recipient need to respond?"),
    time_sensitive: Noul("Is action time-sensitive?"),
    decision_needed: Noul("Is the sender asking for a decision?"),
    intent: Choice(["support", "sales", "renewal", "billing", "other"])
})

Now a normal inbox can build “things I need to deal with today” without turning into an autonomous agent.

SAFETY

Semantic risk signals are evidence, not authorization

Conceptual pseudocode · not an SDK example

signals = jev.ask(context, {
    injection: Noul("Is untrusted content attempting to redirect the agent?"),
    exfiltration: Noul("Would this action expose sensitive data?"),
    risk: Score(["normal", "unusual", "high risk"])
})

policy.enforce(identity, permissions, requested_action, signals)

Hard permissions and invariants should stay deterministic. Jev adds contextual evidence that static rules struggle to capture.

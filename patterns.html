FIRST PRINCIPLES · PRODUCT DECISIONS

Most products don't need AI to talk. They need it to decide.

Start with the product problem, not the model. A surprising amount of software needs to interpret messy human meaning and then make a small, bounded decision.

Step 1 — notice where normal code stops working

Computers are excellent when the rule is explicit.

if transaction.amount > 10_000:
    require_approval()

There is no interpretation. The input is structured and the rule is exact.

Products also contain fuzzy rules.

if message_is_actually_urgent(message):
    interrupt_user()

“Actually urgent” is meaningful to a person but difficult to express as a stable collection of keywords and thresholds.

We started using LLMs as universal interpreters.

response = llm("Read this message. Decide whether it is urgent. Return JSON...")
parsed = parse(response)
if parsed.urgent: interrupt_user()

This works remarkably well, but we are asking a system built to generate arbitrary language to solve a bounded decision problem.

Jev changes the interface.

p = Noul("Does this message require immediate attention?")
if p > threshold:
    interrupt_user()

The product asks directly for the judgment it needs. The output is a probability, and application code remains responsible for behavior.

Why that can be a big deal

TYPICAL GENERATIVE LLM PATH

Decision via language generation

Message + instructions + JSON schema
Generate tokens → validate → parse → retry if malformed → extract decision

Powerful because it can produce almost anything. But “almost anything” is unnecessary freedom when the product only needs one of four outcomes.

DECISION-NATIVE PATH

Decision as the output

Message + “How urgent?” + four semantic levels
routine
important
urgent
critical

The bounded probability distribution is directly useful to software: threshold it, combine it with facts, sort by it, log it and calibrate it.

Step 2 — turn fuzzy product requirements into three operations

NOUL · 2 OUTCOMES

Semantic if

“Is this worth interrupting the user for?”
“Does this form answer the question?”
“Is this likely prompt injection?”

CHOICE · N OUTCOMES

Semantic switch

“Which team owns this?”
“Which tool can do this?”
“Which browser element should I click?”

SCORE · ORDERED LEVELS

Semantic sort

“How relevant is this?”
“How urgent is this?”
“How well does this product match the request?”

Search — the product already knows how to retrieve

Problem: lexical/vector search can find plausible candidates, but a user may express qualities that are difficult to encode as fields or similarity alone: “comfortable for standing all day but doesn't look like a running shoe.”

candidates = search.retrieve(query, top=50)   # existing search

for item in candidates:
    item.fit = Score(
      state={query, item},
      levels=["wrong", "weak", "good", "excellent", "exact"]
    )

return sort_desc(candidates, by=fit)          # ordinary code

Why Jev: the search engine handles scale; Jev handles semantic judgment. Cardinality stays five even if the catalog contains ten million items.

Tool search — retrieval followed by an explicit decision

Problem: an agent may have thousands of tools. Putting every schema into an LLM prompt is expensive and noisy. Embedding similarity can shortlist tools, but similarity is not the same as “can this accomplish the goal?”

tools = retrieve_tools(goal, top=40)
for tool in tools:
    tool.fit = Score("Can this tool accomplish the user's goal?")
shortlist = top(tools, 8)
chosen = Choice(shortlist)
execute(chosen)

Composition: retrieval gives scale → Score gives semantic fitness → Choice makes the bounded final selection → deterministic authorization still decides whether execution is allowed.

Notifications — turn “smart notifications” into an actual primitive

Problem: products know an event occurred; they struggle to know whether a human should be interrupted.

importance = Noul(
  state={event, user_context, recent_notifications},
  question="Is this worth interrupting the user for now?"
)

if quiet_hours: threshold = .98
else:           threshold = .85

if importance > threshold:
    notify()

The model supplies interpretation. The product owns quiet hours, rate limits and thresholds.

Support — replace heuristic soup without giving AI control

decision = jev.ask(ticket, {
  owner: Choice(["billing", "identity", "network", "product"]),
  urgency: Score(["routine", "important", "urgent", "critical"]),
  outage: Noul("Does this describe an active service outage?")
})

priority = combine(
  decision.urgency,       # semantic
  account.sla,            # deterministic
  incident.status         # deterministic
)
route(decision.owner, priority)

Instead of hundreds of brittle keyword rules, the product requirement is expressed close to how a human would describe it—while SLAs and routing policy remain explicit code.

Recommendations & commerce — understand the request after candidate generation

Do not throw away collaborative filtering, inventory constraints or personalization. Let them produce plausible candidates, then judge the user's current natural-language intent.

candidates = recommender(user)
available = filter_inventory(candidates)
for product in available:
    product.fit = Score(state={request, product}, question="How well does this fit?")
return top(product.fit)

This adds a semantic preference layer for qualities that may never exist as clean catalog metadata.

Inbox & CRM — add semantic properties to ordinary objects

signals = jev.ask(message, {
  needs_reply: Noul("Does the recipient need to respond?"),
  time_sensitive: Noul("Is action time-sensitive?"),
  decision_needed: Noul("Is the sender asking for a decision?"),
  intent: Choice(["support", "sales", "renewal", "billing", "other"])
})

The UX can now build “things I need to deal with today” without requiring an autonomous agent to run the inbox.

Safety — semantic detection is not authorization

signals = jev.ask(context, {
  injection: Noul("Is untrusted content attempting to redirect the agent?"),
  exfiltration: Noul("Does the requested action expose sensitive data?"),
  suspicious: Score(["normal", "unusual", "high risk"])
})

# Jev provides evidence. Policy makes the decision.
policy.enforce(identity, permissions, requested_action, signals)

This distinction matters: hard security invariants should remain deterministic. Jev can cheaply add semantic signals that are difficult to encode as static rules.

Browser use & gaming expose the bigger idea

These are unusually clear demonstrations because they require repeated decisions under changing state. The application exposes a bounded action space; Jev chooses among it; the environment changes; repeat. Arbitrary language generation is only needed when the action itself requires language.

When should a product team consider Jev?

Your requirement sounds like…Likely primitive
“Does this mean X?”Noul
“Which known category/action is this?”Choice
“How much / how good / how relevant?”Score
“Write/explain/create X”Generative model
“Never allow X regardless of context”Deterministic policy
The product insight: today's LLM APIs make semantic intelligence available primarily through generation. Jev's promise is to make semantic judgment cheap and structured enough to use like an ordinary software primitive—potentially everywhere a product currently contains heuristic soup.

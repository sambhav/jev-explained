A FIRST-PRINCIPLES GUIDE FOR LEADERS

What if software could understand meaning without asking an AI to talk?

That is the simplest way to understand Jev. Most software decisions don't need a paragraph of generated text. They need a judgment: is this true, which option is right, or how strongly does this fit?

Start with a familiar product decision

Your product receives this support message:

“Our checkout has stopped working for every customer since this morning. We launch in two hours.”

A person immediately understands several things: it sounds urgent, it is probably a product/checkout issue, and it may describe an outage. Traditional software does not naturally understand those meanings.

Rules can approximate meaning.

if "stopped working" in text: urgency += 2
if "every customer" in text: urgency += 3
if "launch" in text: urgency += 1

Over time this becomes heuristic soup: incomplete, brittle, language-specific and hard to maintain.

LLMs gave us a universal semantic interpreter.

llm("Read the ticket, decide urgency and owner, return this exact JSON schema...")

This is a huge advance. But an LLM's native product is an arbitrary sequence of tokens. We are using a language generator to manufacture a tiny decision and then parsing the decision back out.

Jev makes the tiny decision the API.

urgent = Noul("Does this require immediate attention?")
owner  = Choice(["checkout", "billing", "identity", "other"])
risk   = Score(["routine", "important", "urgent", "critical"])

Instead of generating an answer about the decision, the system returns probabilities over the decision space.

Normal software remains in control.

if urgent > .90 and account.sla == "priority":
    page(owner)
else:
    queue(owner, risk)

AI interprets meaning. Deterministic code owns policy, permissions, thresholds and actions.

The entire idea in three primitives

Noul → semantic if
“Is X true?”
Probability over two outcomes.
Choice → semantic switch
“Which X?”
Distribution over a bounded set.
Score → semantic sort
“How much X?”
Distribution over an ordered rubric.

Why this is different from a typical LLM call

GENERATION-FIRST

Ask a model to write the decision

state + prompt + formatting instructions + schema
token → token → token → JSON → validation → parsed decision

The flexibility is valuable when we need language. For a bounded decision, most of that output freedom is unused.

DECISION-FIRST

Ask directly for the judgment

state + semantic question + allowed outcomes
checkout
billing
identity
other

The probability distribution can be thresholded, ranked, combined with facts, monitored and calibrated directly.

Why leaders should care

More places for intelligence

If semantic judgment is cheap and fast enough, it can sit inside ordinary product paths—not only chatbot experiences.

Clearer control boundary

The model interprets fuzzy meaning; application code continues to own irreversible actions, security policy and business invariants.

A simpler product abstraction

Teams can express “needs reply?”, “which team?”, or “how relevant?” directly instead of turning every semantic problem into a mini prompt-engineering project.

Use generation for creation. Jev for judgment. Code for control.

The exciting possibility is not simply “a cheaper classifier.” It is that semantic interpretation could become a normal software primitive—cheap enough to use anywhere a product currently has brittle heuristics or an oversized LLM call.

This is an explainer, not a claim that Jev has already proven that outcome. Jev is early access. TypeSafe's performance numbers are primarily its own measurements; accuracy, calibration, latency and cost should be benchmarked on each real workload.

A VISUAL ESSAY ON DECISION MODELS

Decision Models

What Jev is, how to use it, and how it answers without writing a single word

September 2026 · About 20 minutes

Ask a language model a yes-or-no question, and it writes the answer.

It reads your prompt, then produces {"urgent": true} one token at a time. Each token is a full pass through the model. If you want to know how sure it was, you ask for log-probabilities and dig them out. If it reasons first, it writes a few hundred more tokens before it gets to the word you wanted.

Most of the calls an agent makes aren’t requests for prose. They’re decisions. Is this relevant? Which tool? How severe? Does this reply contradict the record? Every one of them is paid for in output tokens and waited on one token at a time.

An LLM writes its answer. A decision model reads it out.

Jev, from TypeSafe, is the first model built entirely around that idea. TypeSafe calls it a System One model, after the fast, automatic half of human judgment. You send it some state and a set of typed questions. It sends back typed, probabilistic decisions: a probability, a distribution over options you define, or a position on a rubric. It never generates text. TypeSafe describes it as “a frontier-intelligence function call” and quotes 70 to 500 ms end to end, at $0.042 per million input tokens, with output free.

Since launch, a wave of open clones has appeared, each guessing at how it works. This essay covers what Jev is and how to use it, then opens it up next to a conventional LLM, races the two on the same questions, walks through the clones, and ends with the uses that only make sense when a judgment costs a tenth of a second.

01 · WHAT IT IS

Three kinds of answer

Jev has three question types, called primitives. Every question you ask is one of them:

  • Noul: is this statement true? You get one probability between 0 and 1.
  • Choice: which of these options? You get the winning option, a probability for every option, and a confidence value. Up to 255 options, defined with each request.
  • Score: where on this rubric? You get a distribution over 2 to 10 ordered levels and its probability-weighted mean, plus a confidence value.

Ask all three about one message:

Two things are easy to misread. A Score of 2.80 is an average position on the rubric, not a 93% chance of the top level. And because Choice options arrive with each request, they can be anything that exists at that moment: the buttons on the current web page, the legal moves in a game, the tools an agent is allowed to call.

What Jev guarantees is the shape. TypeSafe’s claim is that the model never makes a type error: a Choice is always one of your options, a Score always lands on your rubric. What it can’t guarantee is that the judgment is right. That’s what the probabilities are for.

02 · HOW TO USE IT

State in, decisions out

A request has two parts. The state is whatever you want judged: a string, a JSON object or an array of text. The questions are keyed by name, each with a type, instructions and criteria. For a Choice, the criteria are the options, each with a description; for a Score, they’re the ordered levels. The response gives back typed answers under the same names, the model version that answered, and token usage.

Request body · from the API reference
{
  "model": "jev-latest",
  "state": "Help! My payouts have been failing for 3 days.",
  "questions": {
    "is_urgent": {
      "type": "noul",
      "instructions": "Does this convey urgency?",
      "criteria": { "true": "Explicitly time-sensitive", "false": "No urgency expressed" }
    },
    "department": {
      "type": "choice",
      "instructions": "Which team should handle this?",
      "criteria": {
        "billing": "Payments, invoicing, refunds",
        "technical": "Bugs, outages, integrations",
        "sales": "Pricing, upgrades, new accounts"
      }
    },
    "frustration": {
      "type": "score",
      "instructions": "How frustrated is the customer?",
      "criteria": ["Calm", "Frustrated", "Very angry"]
    }
  }
}

There are official Python and JavaScript SDKs, and community clients for Go, Java, Ruby and others. The limits are worth knowing before you design around it: 64k tokens per request, with 32k for the state plus the longest question. Text only, so no images or audio. Rate limits are currently listed at 250,000 tokens per second and 1,200 requests per minute, and TypeSafe says they are adjusting with demand.

Ask everything at once. Each question is evaluated independently against the same state. So one request can carry every question you might need, including ones that turn out not to apply, and your code ignores the irrelevant answers. TypeSafe calls this speculative fan-out, and documents that adding questions barely changes the response time. Its own cookbook reports that batching a 13-question briefing into one call was 12.2× cheaper and 10.0× faster than asking one at a time, with the same answers.

Keep each question atomic. “Is this an urgent billing outage?” is three questions wearing one coat. Because questions can’t see each other, splitting them costs almost nothing, and you combine the answers in code.

Treat confidence as a second axis. The answer tells you what; confidence tells you whether to act. TypeSafe’s guidance is three paths: act when confidence is high, confirm or gather more when it’s middling, hand off when it’s low. And set the bar per action, by what a mistake costs. Try it:

Mind the dependencies. Parallel answers don’t make a whole workflow parallel. A question that needs a tool result has to wait for it, and that’s a second request.

Put together, the division of labour looks like this. Jev takes the bounded judgments: which tool, is this relevant, does this contradict the record, should we ask. A generative model plans and writes. Tools fetch facts. Code checks permissions, does arithmetic and decides what actually happens.

03 · HOW IT’S BUILT

How an LLM answers a question

To see what Jev changes, start with what a conventional LLM does when you ask it for a decision. There are two phases.

Prefill. The model reads your whole prompt in one parallel pass and stores what it computed for each token in a key-value (KV) cache. This part is fast, because every input token is processed at once.

Decode. Now it writes. Each output token needs another full pass through the model, reading the whole KV cache, to produce a distribution over the vocabulary. One token is sampled, appended, and the loop runs again. {"urgent": true} is about seven trips round that loop. Twenty-one yes-or-no checks written as JSON is around a hundred. A reasoning model may spend thousands before the first brace.

Two common tricks help, and neither removes the loop. Structured output masks tokens that would break the schema, so you always get valid JSON, but it’s still written token by token. Logprob scoring reads the probability of each label token (“yes”, “no”) at the first decode step, which gets you a distribution without writing much. But the probabilities of a model trained to chat aren’t trained to be calibrated, and several questions still mean several prompts or a longer output.

How Jev answers

TypeSafe hasn’t published the architecture. It has published three things: a new model architecture, a “parallel sampler” that generates all outputs in a single query, and a training method called Reinforcement Learning for Calibrated Decisions (RLCD), which optimises for honest probabilities rather than human preference. The best public evidence on the rest comes from Archer Hume, who probed the API with more than 10,000 calls. The measurements are solid; the architecture he infers from them is, in his words, speculative.

Measured

State is computed once. One question took about 87 ms (median). Fifteen hundred questions on the same short state took about 610 ms. If each question reprocessed the state, that line would be steep. It’s nearly flat.

Measured

Questions can’t see each other. A secret code placed in the shared state was detected with probability 0.90 to 0.92. The same code placed in a sibling question was detected with probability 0.00.

Measured

Options are judged together. Adding an irrelevant “weather” option shifted the balance between two real options. The options inform one another before the answer is read out; they aren’t scored independently.

Measured

Probabilities track difficulty. Expected calibration error was 0.031 on 1,200 MMLU items. Math problems it got right 32% of the time received a mean probability of 0.30.

Inferred

A plausible build. A causal transformer, possibly a sparse mixture of experts, reads the state once into a KV cache. Each question runs as an isolated branch that attends to the state but not to other questions. A linear read-out and softmax turn each branch’s final hidden state into probabilities, trained with a proper scoring rule. The tokenizer matched none of 192 public tokenizers tested, so the base model is unknown.

That isolated-branch idea is easiest to see as an attention mask. Every question sees the state and itself, never its neighbours:

Line the two pipelines up and the difference is in the loop, not the reading. Both read the input in parallel. The LLM then runs one forward pass per output token. Jev, as far as anyone can tell, runs the questions as parallel branches in one pass and reads the answers straight out of the model’s final layer. No sampling, no parsing, no output tokens, which is why output is free.

The read-out is only useful if the probabilities mean something. If predictions at 80% are right about 80% of the time, a threshold of 0.8 means what you think it means. That’s the point of RLCD, and it’s the part a clone finds hardest to copy.

Why not just use structured output?
ApproachWhat it gives youWhat to compare
Rules or a small classifierEfficient decisions in a narrow, stable domainAccuracy and maintenance as inputs change
LLM with a strict output schemaBroad language ability with a constrained answer formatTask quality, output length, latency, price
LLM with candidate scoringA decision baseline using scores for allowed outcomesHow scores are obtained and calibrated for your task

Typed output is useful, but it doesn’t by itself establish better reasoning or trustworthy probabilities. A short constrained LLM answer can be fast. Compare against the best baseline for your task.

04 · SIDE BY SIDE

The same questions, three ways

Here are three engines answering identical questions. The first is an LLM writing its answer as JSON. The second is the trick most clones use: the same LLM reading label probabilities after prefill, with no decode loop. The third is Jev. Pick a workload and press run.

Three things fall out of it. Most of the gap comes from removing the decode loop: the middle lane is already much faster than writing JSON, and it’s what most clones do. The rest comes from sharing the state across questions and from serving a model built for this. And the gap narrows when there’s one question and a long input. Picking one of 120 actions is dominated by reading the options, not writing the answer.

05 · THE CLONES

Everyone’s building one

Within weeks of launch, open reimplementations were everywhere. They agree on the goal (typed answers, no generation, one pass) and split into four families by how they get there.

Family 1

Read an LLM’s labels

Keep an off-the-shelf causal LLM. Put the question in the prompt, then read the probability of each label token after prefill instead of sampling.

SemIf reads a frozen Qwen3.5-4B. system-one and Kev fine-tune small models and fit temperatures for calibration.

Easiest to build. Each question is still its own prompt unless you add a mask.

Family 2

Tree-masked branches

A causal LLM with a shared state prefix and one branch per question, isolated by an attention mask. Positions reset per branch, so adding a question can’t shift another’s answer.

One Qwen rebuild reads Noul with a sigmoid head and Choice with a pointer head over option states.

Closest to Archer Hume’s inferred design. Calibration takes real training.

Family 3

Encoder classifiers

A bidirectional encoder such as ModernBERT reads state, questions and option markers together and outputs logits for every question in one pass.

Von (395M) reports about 18 ms on Apple GPU. Laya (421M) reports 39.5 ms on a T4. open-jev reconstructs the idea in PyTorch with cross-attending question slots.

Tiny and fast. Less world knowledge; often needs your own data.

Family 4

Diffusion read-out

A discrete diffusion model denoises a whole canvas at once. Put one masked answer slot per question and read each slot’s distribution without ever writing into it.

OpenJev on DiffusionGemma 26B-A4B reports 27 to 32 ms for one to three questions, about 760 ms median at 64 concurrent requests.

Big model, genuinely parallel slots. Early.

What they report against Jev varies, and every number is the author’s own. Von reports 93.5% macro accuracy against Jev’s 97.2% on a 78-case suite. system-one reports 22 of 24 against Jev’s 23 of 24 on its examples. Laya’s base checkpoints score near chance until you fine-tune them. A roundup of open alternatives reports Kev at 0.822 against Jev’s 0.857 on held-out data, and Jev at 0.966 macro accuracy against the best open option’s 0.704 on an out-of-domain benchmark.

The structure is easy to copy. The calibration isn’t.

Removing the decode loop is a weekend project, and most clones hit tens of milliseconds on a laptop. What’s hard is a model that knows enough about the world to judge arbitrary questions, and whose 0.8 really means 80%. That comes from the training data and the objective, which is exactly the part TypeSafe hasn’t published. If your questions are narrow and you have labelled data, a small clone may be all you need, running locally for free. If they’re broad and changing, the gap in the roundups is the thing to test.

06 · UNIQUE USES

What a tenth of a second makes possible

Anything Jev does, an LLM can do slowly. The interesting uses are the ones where slowly means never: a judgment on every keystroke, every tool call, every frame. Here’s what builders have made with it.

Compaction per tool call

Score every old tool call and result for whether it still matters; keep the survivors verbatim instead of summarising. The most-liked community demo so far.

Voice computer use

Pick the intent and target on each partial transcript, before the sentence is finished.

Filter as you scroll

Judge every post in a feed as it appears. A real-time slop detector is one of the most popular demos.

Permission gates

A Noul in front of every agent tool call: is this action allowed by the policy? Fast enough to sit on the hot path.

Semantic if statements

if email feels "urgent". Probably makes judgment part of a language’s syntax; the Hunch gem does it for Ruby.

Rerank, route, check

Score retrieved passages, choose a model or tool, check a citation or a draft reply against policy, all in one request.

Browser agents are mostly small decisions. The browser runtime extracts the controls a page really has, and each becomes a Choice option. Jev picks one; a text model is called only when the action needs words, such as typing a destination. Browser Use’s jev-ultrafast demo completes a Google Flights search in 7.073 seconds after the first page observation.

Conceptual pseudocode · not an SDK example
for step in range(step_budget):
    page = browser.observe()
    if verify_goal(page, goal):
        break

    # Each entry includes an operation and a compatible target.
    actions = build_allowed_actions(page, goal, max_candidates=255)
    if not actions:
        ask_for_help()
        break

    action = choose(state={goal, page}, options=actions)
    if not policy.allows(action) or not browser.is_current(action):
        ask_for_help()
        break

    if action.operation == "TYPE_TEXT":
        text = text_model(goal, page, action.target)
        browser.type(action.target, text)
    else:
        browser.execute(action)
else:
    ask_for_help()  # The step budget ended without verified success.

Choosing an action isn’t permission to run it. The runtime still enforces allowlists, blocks arbitrary code, asks before purchases, rejects stale elements and verifies success independently.

Games are the same loop, faster. TypeSafe’s demo plays Doom from textual game state at roughly ten decisions a second. The engine supplies the legal moves; Jev picks one; the engine executes. For a big action space, score a shortlist first, then make a final Choice. Wikiracing and community builds such as Jev Chess use the same loop.

Choosing what to remember. fast-jev-compaction asks two parallel Nouls for each old tool-call pair: does knowing this call still matter, and is its exact result still needed? Code keeps, truncates or drops each one, pins recent messages, and falls back to summarising if that isn’t enough. The failure to watch for is an old error that becomes relevant again.

The community lists collect dozens more, grouped into triage and routing, agents and computer use, games, content, research and trading. Popularity isn’t evidence; each still needs testing on your own data.

07 · COST & LATENCY

What a faster decision is worth

A decision that’s ten times faster doesn’t make a task ten times faster. Tools, planning, the final reply and the fallback calls when Jev isn’t sure enough are all still there. The calculator compares an LLM-only path with a Jev-first path that sometimes falls back to the LLM. A workflow is one completed task; a round is one model request that must finish before the next begins.

Equations and what’s included · not a benchmark or provider bill

LLM request cost = (input tokens × input price + output tokens × output price) / 1,000,000

Jev request cost = input tokens × Jev price / 1,000,000

Monthly LLM cost = workflows × (rounds × LLM request cost + shared cost)

Monthly Jev-first cost = workflows × (rounds × (Jev request cost + fallback fraction × LLM request cost) + shared cost)

LLM time = rounds × LLM request time + other time

Expected Jev-first time = rounds × (Jev request time + fallback fraction × LLM request time) + other time

Jev output is priced at zero, following launch pricing. Both paths use the same entered input size. Pricing tiers, cache discounts, batch discounts, different tokenizers, additional retries, throughput limits, human review and the cost of errors are not modeled. Per-request times should include network and service delay. This estimates a mean, not p95; the slowest fallback path can still dominate tail latency.

Price source: TypeSafe’s launch announcement, $0.042 per million input tokens with output free, checked 18 September 2026. All other defaults are illustrative.

  • Fallback approaches 100%. You pay for Jev and then the LLM on almost every request.
  • The rest of the task is slow. If a tool takes 20 seconds, faster decisions save only the model’s share.
  • The baseline is already efficient. A fast classifier or short constrained answer leaves less room.

08 · WHERE IT BREAKS

Where it gets things wrong

TypeSafe publishes the places jev-1.13 is jagged, and they’re worth reading before you design a question. The fix is nearly always the same: let the model judge, and let code do the rest.

Weak spotWhat goes wrongWhat to do instead
Literal readingAnswers the exact words, not the intentState the exact condition; put boundary cases in the criteria
Math and numbersNot a calculator; counting is unreliableDo arithmetic in code
Dates and timesReads dates as text, not ordered quantitiesExtract the dates; compare them in code
IndirectionChains of reasoning and double negatives cost accuracyAsk directly; name the relevant parts of the state
Irrelevant detailExtra state acts as a distractorFilter in code; send only the fields that matter
Adversarial contentInstructions inside the state can sway the answerBe explicit in criteria; test with hostile inputs
ContradictionsInstructions and criteria that disagree confuse itMake them say the same thing
Structural invariantsP(yes) and P(not yes) from separate questions needn’t sum to 1Word each question to mean exactly one thing
GenerationIt isn’t trained to write textTurn extraction into bounded choices; use an LLM to write
  • A valid answer can be wrong. A real option isn’t necessarily the right option.
  • A probability needs validation. Check calibration on your own data before trusting a threshold.
  • A judgment isn’t permission. Code, tools and receipts decide what actually happens.

Read it out

For a decade, getting a decision out of a language model meant asking it to write one. Jev and its clones show that the writing was never the point. Read the state once, ask every question in parallel, and read the answers straight out of the model, with probabilities you can act on.

The architecture is out in the open now, copied a dozen ways. What’s left to compete on is the part you can’t see in a diagram: how much the model knows, and whether its 0.8 means 80%.

An LLM writes its answer. A decision model reads it out.

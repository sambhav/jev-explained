A VISUAL ESSAY ON DECISIONS & AGENTS

Decision Models

What changes when the model returns the answer instead of writing it out, explained through Jev

September 2026 · About 15 minutes

It’s 10:04 on launch day, and the support queue is filling up.

You run support for a payments platform. Your agent reads every ticket before a person does: it works out who owns it, how urgent it is and what to do next. A merchant writes:

“Nobody can complete checkout. Every payment fails, and our launch starts in two hours.”

Before your agent can help, it has to make three decisions. Is this an outage? Which team owns it? How bad is it? None of them needs an essay. Each one has a short list of right answers.

Most agents today make those decisions the only way a language model knows how: by writing. The model reads the ticket, generates something like {"team": "checkout", "urgent": true} one token at a time, and your code parses the text back into a decision.

Most of what your agent does is choose. Today, it chooses by writing.

Jev, from TypeSafe, takes a different approach. You define a question and its allowed answers. Jev returns a judgment: a probability, a distribution over your options or a score on a rubric. Nothing is written out, so there’s nothing to parse.

This essay follows your launch-day queue from the first ticket to the last. It covers what the three kinds of answer mean, how they differ from generated text, where they fit inside an agent, what the published recordings and benchmarks show, and when a faster decision barely moves the whole workflow. The teaching examples are scripted, not Jev calls. The measurements are the publishers’ own, and they’re labelled that way.

Every decision has two halves

Before the ticket goes anywhere, one idea that explains the rest of this essay.

Every decision your agent makes has two halves:

  • Judgment: what the model thinks is true. How likely is it that this ticket belongs to Checkout?
  • Policy: what your product does about it. Route it automatically, or ask a person first?

The model owns the first half. Your application owns the second. Generated text tends to blur them: the model writes "team": "checkout" and the decision looks made. A judgment keeps them apart, so you can see how sure the model is and choose what to do about it.

Try it. Pick a ticket, then move the threshold that decides when your product asks a human for help.

The outage routes itself at almost any threshold. The ambiguous ticket splits between Billing and Identity, and at 80% it goes to a person. Raise the threshold and more tickets go to review. The model’s output didn’t change. Your policy did.

Every figure below keeps those two halves apart. Watch which side each step lands on.

Three kinds of answer

The merchant’s ticket needs three decisions, and each one is a different shape of question. Jev has a primitive for each:

  • Noul: yes or no. Does the message describe an outage? You get one probability.
  • Choice: one of the options you define. Which team: checkout, billing, identity or other? You get a probability for every option, so code can see the runner-up too.
  • Score: a position on an ordered rubric. How severe, from 0 (routine) to 3 (critical)? You get a distribution over the rubric and its probability-weighted mean.

Ask all three about the checkout ticket:

For the checkout ticket, the answers come back as 0.96, Checkout at 92% and 2.80 out of 3. Each one meets a rule your application owns: open an incident review, route to Checkout, put it in the priority queue.

Two things are easy to misread. A Score of 2.80 is an average position on the rubric, not a 93% chance of being critical. And Choice options aren’t fixed in advance: you define them with each request. That matters later, when the options are the buttons on a web page or the legal moves in a game.

How would a regular LLM answer?

You could ask an LLM to generate JSON such as {"team":"checkout"}. Structured output constrains the format. The model still generates output tokens in sequence. Jev exposes a specialized interface for judgments; your program receives typed values and probabilities.

Classification and scoring have existed for years. The useful question is whether a model can handle your changing questions accurately, quickly and cheaply enough to use throughout a workflow.

UNDER THE HOOD

Two ways to answer the same ticket

A text-generating model does two jobs. It processes what you sent, which is called prefill. Then it produces the answer one token at a time, which is called decoding. Every generated token depends on the ones before it, so three answers written as JSON come out in sequence.

For a question with known answers, a decision model can skip the writing. TypeSafe documents that the questions in one request are evaluated independently against the same shared state and come back together as typed values.

Both paths end in the same place: your code routes to Checkout and flags priority review. What differs is the shape of the output, and that’s all this figure shows.

Several questions, one situation. The three questions don’t read one another’s answers. If a later question needs an earlier answer, your code starts another request with that new information.

A plausible implementation processes the common context once and lets the question branches reuse it. The exact cache layout, attention pattern, model size and decision head are not publicly established. So it’s worth being clear about which parts are known:

Documented

Typed questions, parallel judgments. The API accepts shared state and named questions, then returns values and distributions. TypeSafe describes RLCD as its training approach for calibrated decisions. Docs ↗

Interpretation

Shared representations and direct readouts. These mechanisms explain how a system like this could work. Archer Hume’s API probes support aspects of shared computation and question isolation, but don’t reveal the implementation. Analysis ↗

Not established

Exact backbone, sparse experts and training recipe. Don’t treat an inferred transformer diagram as a published Jev architecture. A behavioral match can have many implementations.

Six terms, if you need them

Token. A piece of text used by the model: a word, part of a word or punctuation.

Prefill. The input-processing phase of a typical generative LLM. It builds contextual representations before the first output token.

Autoregressive decoding. Generate one token, include it in the context, then choose the next. Those output steps depend on one another.

Readout. A numerical mapping from a model’s internal representation to scores or probabilities. A conceptual way to understand a decision output.

KV cache. Stored intermediate information that a transformer can reuse rather than recomputing earlier context.

Calibration. Whether probabilities match observed frequencies of correctness over many examples. It’s measured over a dataset, not established by a single answer.

Why not just use structured output? Fair question. Constrained decoding already stops a model from inventing a team name. The honest comparison is against the best baseline for your job:

ApproachWhat it gives youWhat to compare
Rules or a small classifierEfficient decisions in a narrow, stable domainAccuracy and maintenance as inputs change
LLM with a strict output schemaBroad language ability with a constrained answer formatTask quality, output length, latency, price
LLM with candidate scoringA decision baseline using scores for allowed outcomesHow scores are obtained and calibrated for your task
JevA service specialized for typed judgments and distributionsThe same task, quality bar and end-to-end workflow

Typed output is useful, but it doesn’t by itself establish better reasoning or trustworthy probabilities. A short constrained LLM response may be far faster than a long reasoning response.

Probabilities make policy visible. If many predictions assigned 80% are right about 80% of the time, the model is calibrated, and your threshold means what you think it means.

THE AGENT LOOP

The refund at 10:19

Fifteen minutes later, a different kind of ticket:

“Two charges appeared for my order. Please refund the duplicate.”

This one isn’t a single decision. It’s a loop: read, interpret, check policy, use a tool, reply. An agent observes a situation, chooses an action and checks what changed. Jev can take the bounded judgments inside that loop. A language model still handles open-ended planning and writing. Code still checks the facts.

Same ticket, four ledgers. Pick one and step through.

Only one of the four ledgers ends in a refund. In the other three, the agent does the right thing by not claiming one:

  • One entry is still pending. Jev is 97% sure the customer wants a refund. That establishes intent, not eligibility. Code sees one settled charge and routes the case for review.
  • No refund permission. The duplicate is real, but this agent can’t issue refunds. Code hands the case to an authorised operator.
  • The tool fails. Every check passes, and the refund call returns a temporary error. No receipt, so no “refunded” message.

A high probability isn’t proof, and an attempted tool call isn’t a result. The judgment tells you what the customer wants. The ledger, the permission check and the tool receipt tell you what’s true.

Which questions can share a request?

Parallel answers don’t make a whole agent parallel. Questions about the same evidence can go in one request. A question that needs a tool result has to wait for it.

Pick the questions your agent asks about the refund ticket, then decide when the payment team’s investigation note arrives.

For a PM, this changes what to measure. Not how fast one call is, but how the whole case goes:

OutcomeDesign choiceWhat to measure
Faster time to resolutionRoute tickets before generating a responseLower p95 resolution time, with no rise in misroutes
Lower service costHandle easy judgments cheaply; escalate the restLower total cost per correct resolution, including review
More reliable agentsCheck evidence after each tool actionMore failures caught at an acceptable false-alarm rate
Better answersFilter and rank retrieved evidenceImproved grounded-answer quality without losing relevant facts

Start in shadow mode: compute the judgment but keep the existing behavior. Label the disagreements, choose a threshold, and compare against rules, a small classifier and a structured-output LLM before you let it route live tickets.

Before you trust any of it for your queue, run the same test on your own workload:

  1. Define the task. Same input, permitted actions and success criteria for every candidate.
  2. Match the baseline to the job. Include your current system, a fast structured-output LLM and a narrow classifier where it fits.
  3. Measure user-visible time. Report p50 and p95, including network, tools, retries and fallbacks.
  4. Measure useful work. Track correct automated outcomes, escalation rate and cost per successful task.
  5. Check uncertainty. Evaluate calibration and errors across the customer segments that matter.

COST & LATENCY

What a faster decision is worth

A decision that’s ten times faster doesn’t make a ticket ten times faster. The rest of the workflow is still there: tools, planning, the final reply, and a fallback call whenever Jev isn’t sure enough.

The calculator compares an LLM-only path with a Jev-first path that sometimes falls back to the LLM. A workflow is one completed task, such as resolving a ticket. A round is one model request that must finish before the next begins. The default is a hypothetical six-round task, not the five steps of the refund walkthrough.

Equations and what’s included · not a benchmark or provider bill

LLM request cost = (input tokens × input price + output tokens × output price) / 1,000,000

Jev request cost = input tokens × Jev price / 1,000,000

Monthly LLM cost = workflows × (rounds × LLM request cost + shared cost)

Monthly Jev-first cost = workflows × (rounds × (Jev request cost + fallback fraction × LLM request cost) + shared cost)

LLM time = rounds × LLM request time + other time

Expected Jev-first time = rounds × (Jev request time + fallback fraction × LLM request time) + other time

Jev output is priced at zero, following launch pricing. Both paths use the same entered input size. Pricing tiers, cache discounts, batch discounts, different tokenizers, additional retries, throughput limits, human review and the cost of errors are not modeled. Per-request times should include network and service delay. This estimates a mean, not p95; the slowest fallback path can still dominate tail latency.

Price source: TypeSafe’s launch announcement, $0.042 per million input tokens with output free, checked 18 September 2026. All other defaults are illustrative.

Three presets show where the advantage shrinks:

  • Fallback approaches 100%. You pay for Jev and then the LLM on almost every request. Move the slider to find where the extra call stops paying off.
  • The rest of the task is slow. If a tool takes 20 seconds, faster decisions save only the model’s share. Try “Slow tools dominate.”
  • The baseline is already efficient. A fast classifier or a short constrained answer leaves much less room to improve. Try “Fast LLM baseline.”

Per-call speed and system speed are different numbers.

What matters is how many calls a ticket needs, which ones depend on each other, and how much time and cost sit everywhere else.

The same shape, elsewhere

Support tickets are one example. The pattern is general: start with data the application already has, ask a bounded question, and use the answer in code.

Search

It can’t recover a document the retrieval step missed.

Tool selection

Choice among permitted tools, including “none fit”.

Choosing a tool doesn’t supply its arguments or authorise the call.

Notifications

Noul: does this need the user’s attention now? Quiet hours stay in code.

A higher threshold trades interruptions for missed events.

Browser agents are mostly small decisions. An agent reads the page, picks an action, runs it and checks the result. The browser runtime extracts the controls it can actually use, so the model never invents a selector. Each candidate pairs an operation with a compatible target. Jev chooses; a text model is called only when the action needs words, such as typing “London” into a destination field.

Conceptual pseudocode · not an SDK example
for step in range(step_budget):
    page = browser.observe()
    if verify_goal(page, goal):
        break

    # Each entry includes an operation and a compatible target.
    actions = build_allowed_actions(page, goal, max_candidates=255)
    if not actions:
        ask_for_help()
        break

    action = choose(state={goal, page}, options=actions)
    if not policy.allows(action) or not browser.is_current(action):
        ask_for_help()
        break

    if action.operation == "TYPE_TEXT":
        text = text_model(goal, page, action.target)
        browser.type(action.target, text)
    else:
        browser.execute(action)
else:
    ask_for_help()  # The step budget ended without verified success.

The Choice options are rebuilt from every page, which is why defining them per request matters. The linked Browser Use demo asks operation and target questions together, then combines compatible answers in code; those questions can’t see each other’s answers. And choosing an action isn’t permission to run it: the runtime still enforces domain allowlists, blocks arbitrary code, asks before purchases, rejects stale elements and verifies success independently.

Games are the same loop, faster. The engine supplies the facts and the legal actions. Jev picks one. The engine executes it deterministically, and the world has moved on by the next decision, so the loop must reject choices based on stale state. For a large action space, score a shortlist first, then make a final Choice. The same composition works for tool search and large catalogs: generate candidates, narrow them with a Score, decide with a Choice.

Choosing what to remember. Traditional compaction asks an LLM to rewrite old context as a summary, and exact paths, errors and constraints can disappear. fast-jev-compaction keeps the original conversation verbatim and asks Jev which old tool calls and results are still worth keeping; code removes the rest. It pins recent messages and falls back to ordinary summarization if pruning isn’t enough. The failure to watch for: an old error that becomes relevant again.

A judgment inside an if statement. Steve Faulkner’s Probably takes the “AI if statement” literally, making semantic judgment part of the language’s syntax:

Illustrative syntax · check the project for its current form
let email = input()

if email feels "urgent" {
    print(llm "Draft a reply" using email)
}

The runtime can compile feels into a Noul, apply a threshold and take the branch normally. Arithmetic, loops and types stay conventional; interpreting human concepts becomes one more expression.

Where it stops helping

None of this is free of caveats.

  • A valid answer can be wrong. Picking a real team avoids an invented team name. It doesn’t prove the team is right.
  • A probability needs validation. Check that predictions near 80% are right about 80% of the time, on your own data.
  • Some work still needs generation. Writing a reply, creating code and working through a new plan are still jobs for generative models.
  • A judgment isn’t permission. The ledger, the permission check and the tool receipt decide what actually happens.

Back to 10:04

The next time a launch-day ticket lands, your agent should decide who owns it, how bad it is and whether to act. And it should hand each of those decisions to your code as a number it can check, not a sentence it has to parse.

The model judges. Your product decides.

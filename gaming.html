GAMING & REAL-TIME SYSTEMS

Choosing actions in a changing game state

A game can require ten decisions every second. The useful output is not an explanation of what the character should do. It is the action itself.

TypeSafe demo: Jev plays Doom from structured textual game state at roughly 10 queries per second. TypeSafe notes that it is not image-based and that a hand-built Doom bot could play better. The demonstration is about fast semantic action selection under changing state. Primary source · Find the game recording.

The real-time loop

The engine supplies facts

Health, ammo, nearby enemies, visible items and legal actions come from the game. Jev does not need to infer physics or invent actions.

Jev interprets what those facts mean

Given health, nearby enemies and available items, a model can choose among legal actions. This is one possible policy; a purpose-built rule system may work better for a particular game.

The engine executes deterministically

Movement, collision, damage and inventory remain game code. The model chooses; the engine enforces the rules.

The world changes and the loop repeats

The next decision sees a different state. This is much closer to a learned policy loop than a conversation.

Conceptual pseudocode · not an SDK example

while not game.finished():
    state = game.observe()
    # Entries pair actions with legal targets, such as "pick up health pack".
    actions = game.legal_actions(state)
    if not actions:
        game.wait_for_update()
        continue

    shortlist = narrow_with_game_rules(actions, limit=255)
    decision = choose(state=state, options=shortlist)
    if game.is_still_legal(decision):
        game.execute(decision)
    # Observe again after the response; the world may have changed.

The example waits for each decision. It does not promise a 100 ms API response. A real-time implementation must specify what the engine does while waiting and reject decisions based on stale state.

The same pattern produces several game systems

NPC

Behavior policy

Personality + world state → Choice([help, trade, flee, fight, investigate]).

GAME DIRECTOR

Pacing

Player state + recent events → choose the next legal encounter, reward or quiet period.

DIFFICULTY

Player challenge

Gameplay signals → Score([bored, comfortable, stretched, overwhelmed]), then adjust within designer limits.

MODERATION

Fast semantic signals

Chat → independent Nouls for toxicity, threats and spam; deterministic policy decides consequences.

Large action spaces: score, shortlist, choose

For a large action space, generate a smaller candidate set before calling Choice. Wikiracing provides an intuitive example: the next action is a link, but a page can have too many links for one Choice. The following is a possible design, not a reconstruction of the publisher’s implementation.

Conceptual pseudocode · not an SDK example

actions = environment.available_actions()
candidates = retrieve_relevant(actions, goal, top=50)
for action in candidates:
    action.progress = score(
        state={goal, action},
        rubric=["irrelevant", "possibly useful", "strong progress"]
    )
shortlist = top_by_score(candidates, 10)
next_action = choose(state={goal, current_state}, options=shortlist)

This same composition applies to tool search, large catalogs and retrieval: a scalable system generates candidates, a semantic score narrows them, then a bounded Choice can make the final contextual decision.

Why gaming matters beyond games

Browser agents, robotics-like control, workflow engines and simulations have the same shape: state → legal actions → semantic policy → deterministic execution → new state. Jev is interesting when that loop needs broad semantic understanding but cannot afford a full generative response at every step.

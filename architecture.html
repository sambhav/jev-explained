ARCHITECTURE & PRIOR ART

How might Jev work?

Separate what TypeSafe has actually disclosed from what we can infer from the API and from adjacent research.

Important: TypeSafe has not published Jev's neural architecture, weights, parameter count, architecture diagram, or the RLCD algorithm. The diagrams below are conceptual models, not claims about undisclosed internals.

What is publicly disclosed?

Decision-oriented interface

Application state plus bounded questions produce typed probabilistic judgments rather than arbitrary generated strings.

Parallel sampling

TypeSafe positions independent decisions as something that can be evaluated in parallel rather than token-by-token output generation.

RLCD

TypeSafe names its training approach Reinforcement Learning for Calibrated Decisions. The detailed algorithm has not been published.

Why runtime-defined choices matter

A traditional classifier usually has a fixed label space learned for a task. Jev's API allows the candidate meanings themselves to arrive at inference time.

# A browser page changes every step
choices = [
  "Search flights",
  "Destination input",
  "Departure date",
  "Continue",
  "Sign in"
]

action = Choice(
  state={goal, current_page},
  question="Which element should I interact with next?",
  choices=choices
)

This resembles conditional classification over a runtime-defined semantic label space. That is much broader than a conventional fixed classifier.

Research ideas that contain pieces of this

NLI / ZERO-SHOT CLASSIFICATION

Natural language as the classifier interface

NLI work showed that arbitrary labels can be represented as natural-language hypotheses and scored as entailment / neutral / contradiction. Universal-classifier research then used this to perform zero/few-shot classification without a dedicated classifier per task.

state = "Internet has been down since yesterday"

P("This is a network problem" | state)
→ 0.94

Building Efficient Universal Classifiers with NLI · Known NLI zero-shot weaknesses

SETFIT / EMBEDDING CLASSIFIERS

Don't use generation when the job is classification

SetFit demonstrated that semantic encoders plus lightweight classification can be dramatically smaller and cheaper than generative approaches for classification. The key difference is that its classifier is normally task/label-specific, while Jev exposes runtime natural-language decisions.

SetFit paper

CALIBRATION

Train probabilities to mean something

RLCR (ICLR 2026) trains language models with calibration rewards based on proper scoring rules. It is independently published work, not evidence of Jev's RLCD implementation, but it illustrates why a decision model might optimize probability calibration directly.

model says P(correct) = .90

Across many predictions near .90,
~90% should actually be correct.

RLCR paper

NON-AUTOREGRESSIVE MODELS

Remove sequential decoding from the critical path

Non-autoregressive research has long explored parallel output generation. Jev's apparent move is simpler conceptually: if the output is a bounded decision rather than language, there is no need to solve arbitrary parallel prose generation.

What could actually be novel?

None of these ingredients is individually unprecedented: classifiers have probabilities, NLI provides natural-language zero-shot classification, constrained decoding bounds outputs, calibration is a mature research field, and non-autoregressive inference has a long literature.

The potentially interesting contribution is the combination:

broad semantic intelligence + runtime-defined decision spaces + parallel inference + probabilities as first-class outputs + calibration-oriented training + no arbitrary generative output requirement.

Questions worth asking TypeSafe

  1. Is Jev fundamentally an encoder/discriminative architecture, or does it retain a language-model-like semantic backbone?
  2. Are candidate choices independently encoded and scored, jointly attended, or handled through another mechanism?
  3. How does latency scale with state length, number of questions, and Choice cardinality?
  4. Does RLCD train the entire representation model or primarily calibrate a post-trained decision system?
  5. Which proper scoring rule or calibration objective does RLCD optimize?
  6. How well calibrated are probabilities under distribution shift?
  7. Does Choice probability mean relative preference only, and how should developers represent “none of the above”?
  8. How much semantic capability is lost versus a similarly sized generative model?

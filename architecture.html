ARCHITECTURE · STEP BY STEP

Jev likely keeps the language model's understanding and removes the language-generation loop

The strongest current evidence suggests a causal Transformer repurposed for decisions: encode shared state once, evaluate isolated questions against it, let each question's options interact, then read probabilities directly instead of generating an answer token by token.

Evidence status: TypeSafe has not published Jev's weights or full architecture. The model below combines TypeSafe's public claims with Archer Hume's 10,000-call black-box study. The causal backbone and especially sparse MoE are inferences, not confirmed implementation details.

First: what a normal LLM does

Suppose the input is a long incident report and the product needs three fields: risk level, whether review is required, and an action tier.

state = incident_report
wanted = {
  risk: [LOW, MEDIUM, HIGH],
  review: [false, true],
  action: [TIER_1, TIER_2, TIER_3]
}

Prefill: understand the input

A decoder-only Transformer processes all known prompt tokens through its layers. This is where the expensive contextual representation of the incident is built. Keys and values can be retained in a KV cache.

incident + instructions
↓
Transformer layers 1 … N
↓
rich contextual state + KV cache

Autoregressive decode: spell out the answer

The model predicts one next token, appends it, runs another decoding step, predicts the next token, and repeats.

{ → "risk" → : → "HIGH" → , → "review" → : → true → …

Even though the application only wants three decisions, the model performs a sequence of token decisions to express them as language or JSON.

The application recovers the decision

text = llm(...)
json = validate_and_parse(text)
use(json.risk)

Constrained decoding can guarantee syntax and restrict tokens, but the basic decode loop still represents the decision through generated tokens.

A strong baseline: constrained parallel readout on an ordinary LLM

The diagram you shared illustrates an important baseline based on the public Qwen2.5 RLCD experiment. You do not need a new foundation architecture to get much of the speedup.

Run the shared context once

Process the document plus schema/prompt and retain the KV cache.

For each field, reuse that cache

Append only the field-specific suffix—such as risk_level—and obtain the final hidden state for that branch.

Use the existing language-model head as a classifier

The LM head produces logits over the whole vocabulary. Ignore almost all of them and keep only the candidate tokens relevant to this field.

full_vocab_logits = LM_head(hidden_state)
keep = logits["HIGH", "MEDIUM", "LOW"]
p = softmax(keep)
# HIGH .9924 · MEDIUM .0068 · LOW .0006

Do the independent fields together

The risk, review and action branches can reuse the same prefilled context and be scheduled as a batch. Application code assembles the final JSON from verified values.

This already explains an important part of the win: if the output space is known, don't spend sequential decoding steps spelling the decision out. Read the model's scores for the outcomes you care about.

What the Jev probes suggest goes further

Archer Hume's experiments point to a more purpose-built decision path than simply masking an ordinary vocabulary head. citeturn0view0

STRONG EVIDENCE

1. Shared state is computed once

Questions appear to share the state but not each other's text. Moving a secret from one question into shared state made it visible to another; leaving it in the sibling question did not. Up to roughly 100 questions, server time barely changed, and a 23k-token state with thousands of questions fits request accounting that counts the state once. citeturn1view0

shared state
↓
one reusable representation / cache
↙   ↓   ↘
question A   question B   question C

Why it matters: fifty decisions about the same long document should not require understanding that document fifty separate times.

STRONG EVIDENCE

2. Questions are isolated branches

Each question can inspect shared state, but sibling questions do not appear to leak information into one another. That makes the API semantics clean: asking an additional safety question should not change the routing question merely because its instructions became part of the prompt. citeturn0view0

LIKELY

3. The backbone is still probably a causal Transformer

Hume argues that Jev's broad knowledge and TypeSafe's description of RLCD as post-training a pretrained language model make a causal decoder the most plausible backbone. The probes cannot rule out a bidirectional encoder, and the underlying pretrained model is unknown. citeturn1view0

This is important conceptually: Jev may not throw away what made LLMs powerful. It can reuse a pretrained model's semantic representations while changing what happens at the end.

STRONG EVIDENCE

4. Choice options are interpreted together, not as fixed independent labels

This is subtler than a normal classifier. Adding an irrelevant fifth option changed the odds between two existing options in repeated probes. If each option had an independent fixed logit followed only by the same softmax, those relative odds should not change. citeturn1view2

question + [bank, provider, customer, unknown]
↓
interpret the option set as a whole
↓
decision representation
↓
probabilities over this runtime-defined set

Why it matters: options define the meaning of the decision. “None of the above” is inherently relative to the other options, and arbitrary browser/tool choices change every request.

INFERRED

5. End with a direct numerical readout

TypeSafe says Jev outputs probabilities in parallel rather than autoregressively generating tokens. Hume's latency probes found that responses with hundreds of options did not behave like thousands of generated output tokens. A simple conceptual readout is:

h = final_decision_representation
z = W·h + b
p = softmax(z)

Another plausible design is pointer-style scoring against each option's own hidden representation. Current probes do not distinguish the two. citeturn1view2

DISCLOSED GOAL, RECIPE UNKNOWN

6. Train the probability distribution, not a verbal confidence claim

TypeSafe calls its method RLCD—Reinforcement Learning for Calibrated Decisions. The exact recipe is unpublished. The objective is conceptually different from asking an LLM to write “90% confident.” If a system predicts 0.8 across many comparable cases, calibration asks whether roughly 80% are actually correct. Hume reports ECE around 0.031 on a recorded 1,200-item MMLU sample, while noting the limitations of that evidence. citeturn1view3

The computational difference

AUTOREGRESSIVE LLM

Understand once, then repeatedly generate

prefill state
↓
predict token 1
↓
predict token 2
↓
predict token 3
↓
…
↓
parse decision

Output latency grows with the generated sequence because every new token depends on the previous one.

JEV MODEL

Understand once, then read decisions

encode shared state
↓
┌ question A ┐ ┌ question B ┐ ┌ question C ┐
↓      ↓      ↓
readout   readout   readout
↓      ↓      ↓
distributions in parallel

The branches still require compute and attention to state. The gain is removing answer-to-answer token dependencies and avoiding repeated reconstruction of shared state.

Why this is more than “JSON classification”

A fixed classifier knows its labels during training. Jev accepts semantic options at runtime. A browser can present 37 clickable elements now and 18 different elements after the click; a tool router can receive a different tool set for every user. The model must understand what those options mean in the current state, compare them, and produce a distribution over that temporary action space.

Choice(
  state = {goal, page},
  options = current_clickable_elements,
  question = "Which action best advances the goal?"
)

That makes it closer to a general semantic policy/readout over runtime-defined actions than a conventional fixed-label classifier.

What we still do not know

Exact backbone

No public weights, parameter count or confirmed base model.

Exact readout

Fixed slots, pointer scoring, reserved labels, or another mechanism remain possible.

RLCD recipe

The calibration training objective and which parameters are updated are unpublished.

Sparse MoE

Hume argues it is plausible/useful, but calls it the least certain architectural inference.

Sources and competing reconstruction

Archer Hume's 10,000-call black-box analysis provides the strongest public behavioral evidence currently available. Niels Rogge's visual explanation and the Qwen2.5-RLCD experiment show a simpler mechanism that can reproduce part of the idea with an ordinary pretrained LLM: prefill once, reuse KV cache, mask to candidate logits, softmax, and assemble structured output in code. That is a useful baseline, not proof of Jev's internals.

The simplest technical summary:

A normal LLM uses a rich semantic representation to predict the next token, repeatedly. Jev appears to reuse the same kind of semantic intelligence but terminate inference in typed probability readouts over the decisions the application actually cares about—and to share the expensive state computation across many such decisions.

ARCHITECTURE · STEP BY STEP

Understand the input once. Read the decisions directly.

A normal LLM first builds a rich representation of the input, then spends additional sequential work generating the answer as tokens. Jev appears to preserve the first part and replace the second with parallel probability readouts over the decisions the application asked for.

Evidence status: TypeSafe has not published the full architecture. This page separates an ordinary-LLM baseline, a public Qwen/RLCD reconstruction, and inferences from Archer Hume's black-box experiments.

1. Both systems still have to understand the input

Take a long incident report. Whether the final output is prose, JSON or a probability, a capable model first needs a contextual representation of that report. In a decoder Transformer this initial pass is prefill; reusable keys and values are stored in the KV cache.

Jev does not make semantic inference disappear. The opportunity is after the state is understood: if the application only wants a bounded decision, do not spend sequential decoding steps spelling that decision out as language.

2. A normal LLM serializes the decision into tokens

Predict one next token

The model maps its current hidden state to logits over the vocabulary and selects the next token.

Feed the token back

That token becomes part of the context for another decoding step.

Repeat until the structured response is complete

The application may only care about HIGH, true and TIER_2, but the model also emits the serialization around them.

Autoregressive output is sequential: later output tokens depend on earlier ones. Constrained decoding can make the JSON valid, but it does not remove that dependency chain.

3. An ordinary LLM can already be turned into a faster decision baseline

The Qwen2.5/RLCD reconstruction in the diagram you shared is important because it isolates the mechanism. Much of the speed advantage can be demonstrated without inventing a new foundation architecture.

Prefill the common context once

Process the document and shared instructions and retain the KV cache.

Fork one small branch per field

Append only the field-specific suffix for risk_level, requires_review or action_tier.

Read scores for allowed answers

The normal LM head produces logits for the full vocabulary. Keep only the candidate tokens relevant to the field, then normalize them.

full_logits = LM_head(hidden_state)
allowed = ["HIGH", "MEDIUM", "LOW", "NONE"]
probabilities = softmax(full_logits[allowed])

risk_level = argmax(probabilities)

Application code assembles the structured result. No braces, quotes or field names need to be generated.

4. Jev appears to make this decision path first-class

Archer Hume's 10,000-call black-box study suggests Jev is more purpose-built than simply masking an ordinary vocabulary head.

STRONG EVIDENCE

Shared state, isolated questions

Many questions can inspect the same state without seeing sibling questions. Server-time scaling was nearly flat across large numbers of questions in Hume's probes.

LIKELY

A pretrained causal Transformer remains underneath

Broad semantic knowledge still needs a capable backbone. The evidence and TypeSafe's post-training language make a pretrained language-model-like backbone plausible, but not confirmed.

STRONG EVIDENCE

Choice options interact

Adding another option can change relative odds among existing options. That suggests the option set is interpreted together rather than each label receiving an entirely independent fixed score.

This is important for runtime action spaces. “None of the above” only has meaning relative to the other choices; browser elements and available tools can change every request.

5. Three architectures side by side

NORMAL LLM

Prefill + sequential decode

Understand state, then repeatedly predict tokens until a response is complete.

CONSTRAINED LLM

Prefill + masked logits

Reuse state, branch per field, and read only vocabulary logits corresponding to valid outcomes.

LIKELY JEV

Prefill + decision-native branches

Reuse shared state across isolated questions, interpret runtime options and return probability distributions directly.

6. Calibration makes the probabilities useful to software

An LLM can generate the characters "confidence": 0.9. That number is still generated content. A decision API instead exposes the distribution produced by its decision mechanism. TypeSafe says RLCD—Reinforcement Learning for Calibrated Decisions—trains around those distributions.

If predictions assigned roughly 80% confidence are actually correct roughly 80% of the time, the probability becomes operationally useful for thresholds and escalation.

The exact RLCD algorithm is not public, so calibration should be measured rather than assumed.

7. Runtime choices make this broader than a fixed classifier

action = Choice(
    state={goal, current_page},
    options=current_clickable_elements,
    question="Which element best advances the goal?"
)

Those elements did not exist during training. A page can expose 37 actions now and 18 different actions after a click. Jev must understand the meaning of the temporary options and compare them in context. That is closer to a general semantic policy over runtime-defined actions than a conventional fixed-label classifier.

8. What remains unknown

Backbone

No confirmed base model, parameter count or weights.

Decision readout

Pointer-like scoring, reserved slots, specialized heads or another mechanism remain possible.

RLCD

The training recipe and exact calibration objective are unpublished.

MoE

A sparse mixture-of-experts design has been hypothesized but has weaker evidence.

Sources

Archer Hume — Jev's Architecture Unmasked provides the strongest public behavioral probing currently available. The Qwen/RLCD visual reconstruction provides the useful simpler baseline: shared prefill, field branches, candidate-logit masking and softmax.

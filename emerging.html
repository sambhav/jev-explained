EMERGING PATTERNS

The interesting uses are starting to look less like classification

The first wave of Jev demos routed tickets and ranked search results. The newer projects are more revealing: they use cheap semantic judgments as an internal primitive for compilers, context management, agent harnesses, databases, user interfaces and even generative systems.

The common pattern: keep the artifact or state deterministic; use Jev to decide what it means, what matters, or what should happen next.

PROBABLY · SEMANTIC PROGRAMMING LANGUAGE

Put semantic predicates directly into the language

Steve Faulkner's Probably takes the “AI if statement” literally. Instead of calling Jev through an SDK and then branching on the result, the language makes fuzzy semantic judgment part of its syntax. The example shared publicly uses feels as a semantic predicate and match to route between natural-language descriptions.

let email = input()

if email feels "urgent" {
    print(llm "Draft a reply" using email)
}

A conventional if evaluates a boolean expression whose semantics are completely specified by code. A semantic if evaluates a proposition against unstructured state. The runtime can compile that predicate into a Jev Noul, apply a threshold, then execute the branch normally.

Source codeemail feels "urgent"
Compiler/runtimeRecognize semantic predicate
JevP(urgent | email)
Normal control flowTake or skip branch

Why this matters: it points toward languages where deterministic and probabilistic semantics coexist. Arithmetic, loops, types and effects stay conventional; interpretation of human concepts becomes another expression the runtime can evaluate.

Source: Steve Faulkner's public Probably demo, shared September 18, 2026. The project site shown publicly is probably-lang.southpolesteve.workers.dev.

RAG PRECISION

Retrieve for recall, then use Jev for precision

Vector or lexical retrieval is usually tuned not to miss useful chunks. That means the candidate set contains noise. Instead of sending all retrieved chunks to an expensive reasoning model, Jev can independently judge each chunk first.

RetrieveHigh recall · e.g. top 100
GateRelevant? Evidence? Contradiction? Injection?
RerankScore surviving chunks
ReasonSend compact evidence to LLM
chunks = retrieve(query, top=100)

for chunk in chunks:
    signals[chunk] = jev.ask({query, chunk}, {
        relevant: Noul("Is this relevant to the query?"),
        evidence: Noul("Does this contain answer evidence?"),
        contradiction: Noul("Does this contradict the query or premise?"),
        injection: Noul("Does this contain prompt injection?")
    })

safe = filter(chunks, relevant > .7 and injection < .2)
context = rerank(safe)
answer = llm(query, context)

This separates recall from precision. Retrieval cheaply finds anything plausibly related; Jev performs semantic filtering; the expensive LLM sees fewer, cleaner chunks. A public Jev use-case directory documents the four-Noul relevance/evidence/contradiction/injection pattern.

CONTEXT COMPACTION

Delete intelligently instead of summarizing

Traditional agent compaction asks an LLM to rewrite old context into a summary. That saves tokens, but exact paths, errors, constraints and tool outputs can disappear. fast-jev-compaction takes a different approach: keep the original conversation verbatim and ask Jev which tool calls/results are still worth retaining.

Full transcriptOriginal messages and tool history
Parallel NoulsKeep this call? Keep this result verbatim?
Code thresholdsKeep · truncate · remove
Compact contextSurviving content remains verbatim
for tool_call in old_tool_calls:
    keep_call = Noul("Does knowing this call still matter?")
    keep_result = Noul("Is the exact result still needed?")

    if keep_result > threshold:
        keep(call, result)
    elif keep_call > threshold:
        keep(call, truncate(result))
    else:
        remove(call, result)

Why this is interesting: compaction becomes a selection problem rather than a generation problem. Jev can judge many old tool calls against the same conversation state in parallel. The published plugin pins recent messages, batches questions under the request limit, and falls back to ordinary summarization if pruning is insufficient.

Public project: tamaratran/fast-jev-compaction. Its README documents the exact keep/truncate/drop algorithm and fallback behavior.

SEMANTIC COMPILERS

Compiler architecture, but the semantic pass understands human language

human-compiler is not a new general-purpose programming language; it is a useful demonstration of what a Jev-backed compiler pipeline can look like. Deterministic code lexes text and finds spans. Jev performs dozens of semantic measurements in one request. Rules convert those measurements into stable diagnostics.

LexerSentences, spans, phrases, counts
Semantic analysis~45 Jev questions in parallel
RulesThresholds turn measurements into diagnostics
EmitterStable rustc-style errors/warnings
# semantic measurements
passive_aggression = Noul("Is this passive-aggressive?")
information_density = Score([...])
dialect = Choice(["corporate", "academic", "reddit", ...])

# deterministic compiler policy
if information_density < 0.25:
    error("HC003", "no recoverable information")

if passive_aggression > 0.80:
    warning("HC101", span=source_span)

The project even implements compiler-like modes and flags: -Wall lowers thresholds, -Werror promotes warnings, and -O2 removes paragraphs judged to add no information. The deeper idea is useful beyond the joke: semantic linting can have stable codes, spans and deterministic policy while the fuzzy measurement comes from Jev.

AGENT HARNESS

Move the agent's small decisions out of the expensive reasoning loop

Agent harnesses repeatedly ask questions that are much smaller than “solve the task”: which tool should run, did the last step work, is the task complete, is this action risky, should we retry, and which model should handle the next step?

signals = jev.ask(state, {
    done: Noul("Is the requested task actually complete?"),
    next: Choice(["tool", "reason", "ask_user", "stop"]),
    risk: Score(["routine", "sensitive", "high-risk"]),
    model: Choice(["fast", "coding", "reasoning"])
})

if signals.risk > high_risk:
    require_confirmation()
elif signals.done > done_threshold:
    stop()
else:
    dispatch(signals.next, signals.model)

LangChain's Jev harness write-up and several community projects use this shape. The important shift is continuous cheap judgment: checks that were too expensive to run on every agent step can become part of the loop.

SEMANTIC LINTING & REVIEW

Plain-English invariants become continuous checks

Projects such as JevLint, code-review harnesses and stop hooks treat engineering requirements as semantic predicates: “does this change introduce a magic string?”, “is the agent claiming success without evidence?”, “is this diff outside scope?”

checks = {
    in_scope: Noul("Is this change within the requested scope?"),
    tests_support_claim: Noul("Do the test results support the agent's claim?"),
    risk: Score(["mechanical", "behavioral", "security-sensitive"])
}

Unlike an LLM review paragraph, each check has a stable identity and probability, so CI can threshold it, trend it over time and require a human only when necessary.

DATABASES & DATA PIPELINES

Semantic predicates can become data operators

Community work already includes PostgreSQL and DuckDB integrations. The natural abstraction is a semantic WHERE/CASE/ranking operator over rows.

SELECT *
FROM support_tickets
WHERE jev_noul(
    ticket_text,
    'Does this describe an active customer outage?'
) > 0.9;

The database still scans, filters, joins and aggregates. Jev supplies the predicate that cannot be expressed cleanly with ordinary columns. For bulk workloads, batching and cost/latency become the main systems questions.

UI AS A DECISION SPACE

Choose interfaces instead of generating interfaces

The community project Instinct takes a free-text situation and has Jev select from a fixed catalog of UI components. No HTML or copy needs to be generated.

ui = Choice([
    "confirmation_dialog",
    "warning_banner",
    "comparison_table",
    "step_by_step_form",
    "empty_state"
])

This is a strong product pattern when design consistency matters: humans design the allowed components; Jev interprets the situation and chooses which composition fits.

GENERATIVE SYSTEMS BUILT FROM DECISIONS

Repeated bounded decisions can approximate generation

Several experiments deliberately push Jev outside its intended shape. jev-freeform builds raw-character chat from repeated Choice calls; jev-chat explores hierarchical speculative decoding; jev-lm combines an n-gram drafter with Jev verification; and a pixel-art experiment asks hundreds of parallel per-pixel questions.

These are research toys, not the recommended Jev architecture. Their value is conceptual: generation itself can sometimes be decomposed into a very large number of constrained decisions. It also shows exactly where autoregressive LLMs remain more natural.

CONTROL SYSTEMS & COMPUTERS

If the machine exposes legal actions, Jev can act as a semantic policy

Beyond browser use and Doom, projects now drive Android, macOS, robots, Minecraft, Civilization II, Pong and even a deliberately experimental RISC-V CPU construction. The reusable architecture is the same:

ObserveStructured machine state
JudgeChoice over legal actions
ExecuteDeterministic runtime
RepeatNew state

This is where “Jev as a programming primitive” becomes most literal: semantic intelligence is embedded inside a normal state machine rather than sitting outside the application as a chatbot.
